# 应用数据库架构

## 当前决策

`Image Color Remover App` 使用它**自己的** Cloudflare Worker 和 D1 数据库：

- Worker：`image-color-remover-app`
- D1：`image-color-remover-app-db`
- 正式应用域名：`app.imagecolorremover.com`
- 现有静态工具站：`imagecolorremover.com`（不替换、不共用运行时数据库）

## 为什么不把未来所有网站的登录数据库合在一起

数据库数量本身通常不是早期的主要成本；真正容易产生成本和风险的是图片/视频存储、AI 调用、邮件和大量读写。把不同产品的用户、会话、积分和支付记录放进同一个登录库，会带来这些问题：

1. 一个应用的迁移或故障会波及全部网站。
2. 用户删除、退款、权限审计和隐私请求很难只针对一个产品处理。
3. 不同产品的积分或订阅可能被意外串用。
4. 将来拆分或出售某一个产品时，数据很难干净迁移。

所以早期采用“**每个需要登录的应用：一个 Worker + 一个 D1**”的隔离方式。每个应用只保存自己的账户、会话、积分、订单和配置。

## 未来怎样共享，才不会浪费

当多个应用真的需要统一登录时，再单独建立一个“账户中心”服务，只共享最少的身份字段（例如内部用户 ID、邮箱验证状态）。积分、订单、编辑记录和产品配置继续留在各自应用数据库中。

运营统计可以后续汇总到独立的分析库；它不参与用户登录或付费的实时链路。

## 成本控制原则

- 首发不保存原图或 AI 结果：处理结果只返回给当前用户下载。
- 人像清理按次消耗积分，失败自动退回，不让异常调用持续扣费。
- 只有当用户确实需要历史记录、云端项目或批量处理时，才增加 R2 对象存储。
- 观察真实调用量后再升级付费计划，不提前为“可能会有的流量”付费。
